## 代表性技术案例

**平台框架层的通知机制缺陷定位**

现象：某方法调用将返回值写回表单变量后，依赖该变量解析目标表单的组件不再重新解析，右键进入明细失败。

排查过程：

1. **隔离分歧点**——写回操作存入了值，但未向该变量的注册依赖方触发变更通知
2. **设计实验将问题空间减半**——在同一事件链中从表单脚本读取该变量，返回值正确。由此证明"存储正常、通知缺失"，排除了一半可能性
3. **拒绝接受未被理解的 workaround**——发现一个值相同的自赋值可以绕过问题；该操作不改变任何值，唯一效果是触发通知副作用。将这一推理完整写入报告
4. **以框架自身的文档化先例作为证据**——框架中存在"仅设值"与"设值并标记修改、通知刷新"两个平行 API，推断写回路径走了非通知分支
5. **提出两个精确的设计问题而非要求修复**——写回是否应当触发通知以与表单脚本行为一致？若不应，受支持的重新解析方式是什么？
6. **说明架构影响**——所有已迁移表单都将被迫保留一行形似死代码的脚本，而这与该架构改造项目"减少表单脚本"的准则直接冲突，且极可能在评审中被删除或在迁移中丢失
7. 记录精确的平台版本与构建号

**结果**：将一个"某表单右键失效"的表象问题，转化为一份含复现、证明、workaround、机制解释与战略影响分析的框架设计质询，对平台团队具备独立价值。

## 一、v3 相对 v2 改了什么，以及为什么

v2 是基于你**口述的自我评价**写的，而那个自我评价与 Jira 记录不符——低估了大约两个级别。v3 基于可核验的工单记录重写。

三处结构性改动：

1. **不再按"修 bug / 开发功能"分类，改为按能力层级分节。** 因为你的真实卖点不是"我做过什么类型的任务"，而是"我处在哪个决策层级"。规范撰写、架构分层、平台级根因分析——这三样是分水岭，v2 里一个都没有。
2. **新增「代表性技术案例」独立成节。** 那个平台通知机制的排查过程是你最值钱的单一资产，它证明的不是"我会修 bug"，而是"我能在自己产品的下一层做设计质询"。技术面 80% 的话题应该由这一段引出。
3. **期望薪资从 18–22K 上调到 22–25K。**

## 二、期望薪资为什么是 22–25K，不是 30K

**支撑 22K 以上的（可迁移）**：规范撰写、架构分层决策、平台层根因分析、测试矩阵设计、SOLID 的真实落地、代码评审与规范执行、技术英语写作。这些换到任何一家企业软件公司都成立。

**压低估值的（不可迁移）**：738 个工单里 725 个在同一产品，技术栈集中在 C# + SQL Server + Mongoose/SyteLine，**没有云、容器、CI/CD 或第二语言生态的任何记录**，没有带人经验。出了 Infor 生态，Mongoose 专精会被打折。

所以 22–25K 是一个你能用事实撑住、面试时不会被问倒的数字。25K 以上需要两个条件之一：对方本身在用 SyteLine / 需要 Mongoose 能力（Infor 合作伙伴、跑 CSI 的甲方），或者你在通用工程问题上面试表现突出。

**谈判时不要主动降价。** 你自己说过"12–15K 就挺 OK"——这句话心里可以有，绝不能说出口。那可能是你市场价的一半。
